The 80% Reality

The "Messy Data" Janitor

In tutorials, data is pristine. In enterprise environments, 80% of a Data Scientist's time is spent on data hygiene. An IoT sensor cluster failed, resulting in corrupted database entries. Fix them.

Trap: Mean vs Median Imputation

Using the mean when outliers exist (like Temp=9999) heavily skews the distribution. Always prefer median or robust imputation for sensor data.

Trap: Silent String Errors

" Active " and "active" are treated as distinct categorical variables by models. Standardizing strings via `.str.lower().str.strip()` is mandatory.

Classification Paradigm

The 1% Problem & SMOTE

The accuracy paradox in fraud/cancer detection. If 99.9% is normal, a model predicting "Normal" 100% of the time gets 99.9% accuracy but fails in business.

SMOTE Visualization

Synthetic Minority Over-sampling Technique (SMOTE) generates synthetic samples along the line segments connecting minority class nearest neighbors.

Production Techniques

Handling a 0.05% positive rate in banking fraud requires more than just SMOTE.

1. Class Weighting

clf = RandomForestClassifier(class_weight='balanced')

Penalizes the model heavily for misclassifying the minority class during training.

2. Threshold Tuning

y_pred = (model.predict_proba(X)[:, 1] > 0.15).astype(int)

Default threshold is 0.5. Lowering it increases Recall (catches more fraud) at the cost of Precision (more false alarms).

3. Right Metrics

Never use Accuracy. Use PR-AUC (Precision-Recall Area Under Curve) and F1-Score to evaluate imbalanced classifiers.

import joblib
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.ensemble import RandomForestClassifier

# 1. Define Pipeline (No data leakage, easily serializable)
pipeline = Pipeline([
    ('scaler', StandardScaler()),
    ('classifier', RandomForestClassifier(n_estimators=100))
])

# 2. Train
pipeline.fit(X_train, y_train)

# 3. Serialize Artifact
model_metadata = {
    'version': '1.2.0',
    'features': ['age', 'income', 'credit_score'],
    'pipeline': pipeline
}
joblib.dump(model_metadata, 'model_v1.2.0.joblib')
print("Model saved to registry successfully.")
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import joblib
import numpy as np

app = FastAPI(title="Fraud Detection API")
model_data = joblib.load('model_v1.2.0.joblib')
pipeline = model_data['pipeline']

# Strict Data Validation Schema
class InferenceRequest(BaseModel):
    age: float
    income: float
    credit_score: float

@app.post("/predict")
async def predict(req: InferenceRequest):
    try:
        # FastAPI async handling for high concurrency
        features = np.array([[req.age, req.income, req.credit_score]])
        pred = pipeline.predict(features)[0]
        prob = pipeline.predict_proba(features)[0][1]
        
        return {"fraud_prediction": int(pred), "probability": float(prob)}
    except Exception as e:
        raise HTTPException(status_code=400, detail=str(e))

Generative AI

Enterprise LLMs & RAG

Why enterprises use Retrieval-Augmented Generation (RAG) instead of raw LLMs: eliminate hallucinations, utilize private data, and prevent security leaks.

The RAG Pipeline

Implementation (LangChain)

from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.chains import create_retrieval_chain
from langchain.chains.combine_documents import create_stuff_documents_chain
from langchain_core.prompts import ChatPromptTemplate

# 1. Connect to existing Vector Database
vectorstore = Chroma(persist_directory="./chroma_db", embedding_function=OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# 2. Define System Prompt for Strict Grounding
system_prompt = (
    "You are an IT Helpdesk assistant. "
    "Use ONLY the following retrieved context to answer the question. "
    "If you don't know the answer based on the context, say 'I don't know'."
    "\n\nContext: {context}"
)
prompt = ChatPromptTemplate.from_messages([
    ("system", system_prompt),
    ("human", "{input}"),
])

# 3. Create RAG Chain
llm = ChatOpenAI(model="gpt-4-turbo", temperature=0)
question_answer_chain = create_stuff_documents_chain(llm, prompt)
rag_chain = create_retrieval_chain(retriever, question_answer_chain)

# 4. Execute
response = rag_chain.invoke({"input": "How do I request a new AWS account?"})
print(response["answer"])

Enterprise Interview Q&A

Top 5 tough questions asked in Machine Learning Engineer interviews.

1. How do you detect and fix data drift in production? +
I monitor input distributions (Covariate Shift) using metrics like Population Stability Index (PSI) or Kullback-Leibler (KL) divergence via tools like Evidently AI or Prometheus. If drift exceeds a threshold (e.g., PSI > 0.2), it triggers an alert. To fix it, I analyze the shifting features, relabel recent ground-truth data, and initiate an automated retraining pipeline on a rolling window of recent data, followed by shadow deployment to verify the fix.
2. Why is Accuracy dangerous for fraud detection? +
Fraud is a highly imbalanced problem (e.g., 0.1% fraud rate). A naive model that predicts "Not Fraud" for every transaction achieves 99.9% accuracy but provides zero business value. Instead, I use PR-AUC (Precision-Recall Area Under Curve), F1-Score, and look at the Confusion Matrix. We must tune the decision threshold to balance False Positives (annoying customers) and False Negatives (financial loss).
3. Walk me through serving a Scikit-Learn model via FastAPI in Docker. +
First, encapsulate the entire preprocessing and modeling step into a Scikit-Learn Pipeline to prevent data leakage, then serialize it using joblib. Create a FastAPI app, loading the model into memory upon startup. Define strict input schemas using Pydantic to validate API requests. Write a Dockerfile using a lightweight base image (like python:3.11-slim), copy the code/model, install dependencies, and run the app via Uvicorn/Gunicorn. Finally, deploy the container to a service like AWS ECS or Kubernetes.
4. Fine-Tuning an LLM vs RAG: When to choose which? +
RAG (Retrieval-Augmented Generation) is best for giving the model access to private, changing, or highly specific knowledge without retraining. It prevents hallucinations by grounding answers in retrieved documents. Fine-tuning is best when you need the model to learn a specific style, format, or behavior (e.g., speaking like a pirate or outputting strict JSON) that prompting alone can't achieve efficiently. They are often combined: RAG for knowledge, fine-tuning for behavior.
5. How do you handle cold-start and real-time features? +
For real-time feature retrieval (e.g., "number of transactions in the last 5 minutes"), batch databases are too slow. I utilize a Feature Store (like Feast). Batch features (historical data) are calculated in Airflow/Spark and stored in an offline store (like Snowflake) for training. Real-time features are computed via streaming (Kafka/Flink) and written to a low-latency online store (like Redis). The API queries Redis for sub-millisecond feature retrieval during inference.
