Data, DBMS, RDBMS & Dr. E.F. Codd's 12 Relational Rules

From raw unorganized facts to mathematically rigorous relational database engines: Master the 12 Codd rules and enterprise data type memory footprints.

🏢 Data vs Information vs DBMS vs RDBMS

1. DATA (Raw Facts): Unorganized observations (e.g. [42, 'Bangalore', 1200]).
2. INFORMATION (Contextualized): Structured facts with business meaning (e.g. "Customer #42 spent $1,200 in Bangalore store").
3. DBMS (Software): Program to store/retrieve files (e.g. hierarchical, file systems, NoSQL).
4. RDBMS (Relational + ACID): Mathematical table relations, primary-foreign keys, and ACID transaction guarantees (e.g. Oracle, PostgreSQL).

📜 Dr. Edgar F. Codd's 12 Relational Database Rules

Mathematical Relational Standard
Rule 0: Foundation Rule

The system must manage the database entirely through its relational capabilities.

Rule 1: Information Rule

All data and metadata are stored solely as values in table cells.

Rule 2: Guaranteed Access

Every atomic cell is reachable via: Table Name + Primary Key + Column Name.

Rule 3: Systematic NULLs

NULL is distinct from 0 or empty string; represents missing/unknown values.

Rule 4: Online Catalog

Schema dictionary is queried using the exact same relational SQL syntax.

Rule 5: Comprehensive Sublanguage

Must support at least 1 language for DDL, DML, DQL, TCL, and DCL.

Rule 6: View Updating

All theoretically modifiable views must be updatable by the RDBMS engine.

Rule 7: Set-Level Operations

INSERT, UPDATE, DELETE act on entire sets of records at once, not row loops.

Rule 8: Physical Data Independence

Changing disk storage or B-Tree indexes does not alter SQL queries.

Rule 9: Logical Data Independence

Schema refactoring (adding columns) does not break user views.

Rule 10: Integrity Independence

Constraints reside inside the RDBMS catalog, not client frontend code.

Rule 11: Distribution Independence

SQL runs identically on local single servers or distributed multi-node clusters.

Rule 12: Non-Subversion Rule

Low-level record interfaces cannot bypass relational constraints or security.

Foundation

Constraints & Referential Integrity

Think of constraints like the bouncers at a club. They ensure that only valid, high-quality data enters your tables, keeping your database clean and error-free.

🎬 Real-World Dramatic Story: Netflix Subscriber Deduplication Incident During a massive global rollout, Netflix's registration API had a bug. Because the `email` column lacked a `UNIQUE` constraint, millions of duplicate accounts were created. It took a whole week to clean up the mess. The DBA team was furious. A simple `UNIQUE` constraint would have blocked the duplicate inserts instantly at the database level!

The 6 Key Constraints

  • PRIMARY KEY Uniquely identifies each row (NOT NULL + UNIQUE).
  • FOREIGN KEY Links to another table's PK. Maintains referential integrity.
  • UNIQUE Ensures all values are different.
  • CHECK Validates conditions (e.g., age > 18).
  • NOT NULL Ensures a column cannot have a NULL value.
  • DEFAULT Provides a default value when none is specified.

Nullability & Logic

NULL Handling & Conditional Functions

NULL means "Unknown" or "Missing". We need special functions (NVL, NVL2, NULLIF, COALESCE, DECODE) to handle these black holes.

🎬 Real-World Dramatic Story: Amazon Missing Seller Data Defaults Amazon calculates final payout = `Sales - Commission - Penalty`. If a new seller had no penalty logged, the database returned NULL. The math `1000 - 100 - NULL` resulted in a NULL payout! Adding `NVL(Penalty, 0)` saved the finance team from a disaster.

NULL Functions

  • NVL(col, val) If col is NULL, return val. Else return col.
  • NVL2(col, val1, val2) If NOT NULL return val1, else val2.
  • NULLIF(e1, e2) NULL if both equal, else e1.
  • COALESCE(e1, e2...) Returns FIRST non-null expression.

DECODE() Function

Oracle's IF-THEN-ELSE. Replaced by CASE WHEN, but tested heavily.

DECODE(col, search1, res1, search2, res2, default)
CASE WHEN vs DECODE: CASE WHEN is ANSI SQL and supports inequalities (>, <) while DECODE is Oracle-specific and only checks equality (=).

Advanced Execution

Correlated Subqueries Deep Dive

A Correlated Subquery is evaluated ONCE FOR EVERY ROW processed by the outer query.

🎬 Real-World Dramatic Story: Banking Fraud Detection Alert A bank wanted to find accounts whose current withdrawal exceeded the AVERAGE withdrawal for that specific branch. Since every branch has a different average, the database calculated the average withdrawal row-by-row for millions of transactions using a Correlated Subquery!

Visual Walk-through of Execution

SELECT outer.ename, outer.sal FROM Emp outer WHERE outer.sal > ( SELECT AVG(inner.sal) FROM Emp inner WHERE inner.deptno = outer.deptno );

Step 1: Outer fetches Row 1 (Ravi, Dept 10, Sal: $5000).

Step 2: Subquery calculates AVG(sal) specifically for Dept 10 ($4500).

Step 3: Evaluates: Is $5000 > $4500? True. Keep row.

Step 4: Outer fetches Row 2... repeats step 2 & 3.

SQL Language Classification & Table Lifecycle

Understanding Database Management Systems (DBMS), Relational Models (RDBMS), the 5 SQL Sub-Languages, and the internal mechanics of DDL vs DML commands.

🎬 Real-World Dramatic Story: The Midnight Wall Street Bank Heist Recovery At 2:45 AM, an errant deployment script executed DROP TABLE Ledgers; on a major investment bank's primary Oracle cluster instead of staging. Because DROP is a DDL command, it auto-committed immediately. Disaster was averted within 90 seconds because the lead DBA used Oracle's FLASHBACK TABLE Ledgers TO BEFORE DROP; to rescue all transaction logs directly from the database recycle bin!
DDL Auto-Committed

Data Definition Language

Defines, modifies, and deletes database schema objects. DDL statements execute an implicit COMMIT.

  • CREATE — Instantiate tables, views, indices
  • ALTER — Add, modify, drop columns/constraints
  • DROP — Permanently remove table & schema
  • TRUNCATE — Empty table data, reset High Water Mark
  • RENAME — Rename schema objects
DML & DQL Rollbackable

Data Manipulation & Query

Manipulates row-level data inside tables without modifying table structure. Requires explicit transaction commit.

  • INSERT — Add new records into table
  • UPDATE — Modify existing row values
  • DELETE — Selectively remove rows with WHERE
  • SELECT — (DQL) Project and filter dataset
TCL & DCL Security & ACIDs

Transaction & Access Control

Manages atomicity, rollback points, and user permission boundaries across the multi-user database.

  • COMMIT — Persist current transaction to disk
  • ROLLBACK — Undo uncommitted modifications
  • SAVEPOINT — Set named rollback checkpoints
  • GRANT / REVOKE — User access permissions

📐 Nested CASE Statement Syntax

A CASE expression nested inside the THEN clause of an outer CASE statement:

Nested CASE Blueprint SQL
CASE WHEN CONDITION1 THEN CASE WHEN CONDITION2 THEN RESULT1 ELSE RESULT2 END WHEN CONDITION3 THEN CASE WHEN CONDITION4 THEN RESULT3 ELSE RESULT4 END ELSE RESULT5 END

💡 1. Why Do Joins Exist? Database Normalization (1NF ➔ 3NF)

If we stored employee names, salaries, department names, and department locations in a single monolithic table, updating department location from 'DALLAS' to 'AUSTIN' would require updating thousands of duplicate employee rows (risk of **Update Anomalies**). By normalizing database tables into separate entities (EMP and DEPT) linked by a foreign key (DEPTNO), we eliminate redundancy while maintaining relational integrity. SQL Joins reconstruct the complete dataset at query time.

⚠️ 2. The #1 SQL Interview Trap: ON vs WHERE Filtering in LEFT JOIN

FAANG Interview Favorite

Adding a condition to the ON clause behaves fundamentally differently than placing it in the WHERE clause during an Outer Join!

✅ Case A: Filtering in the ON Clause 
SELECT e.ename, d.dname, d.loc
FROM Emp e
LEFT JOIN Dept d 
  ON e.deptno = d.deptno 
 AND d.loc = 'DALLAS';

Result: Preserves ALL 14 employees! If an employee is not in DALLAS, department columns return NULL, but the employee is NOT filtered out.

❌ Case B: Filtering in the WHERE Clause 
SELECT e.ename, d.dname, d.loc
FROM Emp e
LEFT JOIN Dept d 
  ON e.deptno = d.deptno
WHERE d.loc = 'DALLAS';

Result: Converts LEFT JOIN into an INNER JOIN! Because non-matching left rows produce d.loc = NULL, and NULL = 'DALLAS' is FALSE, all non-DALLAS rows are discarded.

⚙️ 3. Physical Database Execution Algorithms (Hash Join vs Nested Loop vs Sort-Merge)

How relational query optimizers (Oracle CBO, PostgreSQL, Snowflake) physically join datasets on disk/memory:

Join Algorithm Time Complexity Memory Requirement Best Database Workload Scenario
Nested Loop Join $O(M \times N)$ $O(1)$ Minimal Memory Small tables, or when outer table drives indexed lookups on inner table (OLTP applications).
Hash Join $O(M + N)$ $O(M)$ Hash Table in RAM Joining large unindexed tables in Data Warehouses (Snowflake / Redshift). Builds in-memory hash map of smaller table.
Sort-Merge Join $O(M \log M + N \log N)$ $O(1)$ if pre-sorted When join columns are already sorted (B-Tree index scans) or when inequality range joins (`JOIN ON e.sal >= s.losal`) are used.

👑 4. 3-Tier Corporate Chain of Command Self-Join

Joining a table to itself to resolve recursive parent-child relationships (e.g. Employee ➔ Direct Manager ➔ VP Executive Boss).

3-Tier Hierarchy Query SQL
SELECT e1.ename AS Employee, e1.job AS Emp_Role, e2.ename AS Direct_Manager, e3.ename AS Executive_VP_Boss FROM Emp e1 LEFT JOIN Emp e2 ON e1.mgr = e2.empno LEFT JOIN Emp e3 ON e2.mgr = e3.empno ORDER BY Executive_VP_Boss, Direct_Manager;

The Complete Window Functions Encyclopedia (All 18 Functions)

A window function performs a calculation across a set of table rows that are related to the current row without removing or collapsing individual rows. Master partitions, orderings, and sliding window frames.

📊 Visual Anatomy of a Window Partition

Consider computing AVG(sal) OVER (PARTITION BY department). Unlike GROUP BY which collapses rows into one line per dept, the window function retains every single employee while broadcasting their department average alongside!

💻 IT Department Window (Partition 1)
• RAVI — Sal: $50,000 ➔ Dept Avg: $60,000
• ARUN — Sal: $70,000 ➔ Dept Avg: $60,000
👥 HR Department Window (Partition 2)
• PRIYA — Sal: $60,000 ➔ Dept Avg: $70,000
• ANU — Sal: $80,000 ➔ Dept Avg: $70,000

1. RANK()

Gaps After Ties

Assigns the same rank to rows having equal values. Gaps are left after tied ranks (e.g. 1, 2, 2, 4).

-- Display salary rank of each employee within their dept with highest salary receiving rank 1 SELECT ename, deptno, sal, RANK() OVER (PARTITION BY deptno ORDER BY sal DESC) AS sal_rank FROM Emp;

2. DENSE_RANK()

No Gaps After Ties

Assigns the same rank to tied rows but does NOT leave gaps after ties (e.g. 1, 2, 2, 3). Crucial for finding the true Nth highest salary.

SELECT ename, deptno, sal, DENSE_RANK() OVER (PARTITION BY deptno ORDER BY sal DESC) AS sal_dense_rank FROM Emp;

3. NTILE(N)

Equal-Sized Buckets

Divides rows into approximately equal-sized groups or buckets and assigns each row a bucket number (e.g. Quartiles 1–4).

-- Divide all employees into 4 salary quartile groups with highest paid in group 1 SELECT ename, sal, NTILE(4) OVER (ORDER BY sal DESC) AS salary_quartile_group FROM Emp;

4. PERCENT_RANK()

Relative Rank 0.0 to 1.0

Calculates the relative rank of a row within its partition producing a floating-point score between 0 and 1: $\frac{\text{Rank} - 1}{\text{Total Rows} - 1}$.

SELECT ename, deptno, sal, PERCENT_RANK() OVER (PARTITION BY deptno ORDER BY sal) AS salary_percent_rank FROM Emp;

5. CUME_DIST()

Cumulative Distribution

Returns the proportion of rows whose ordering value is less than or equal to the current row value: $\frac{\text{Count}(\text{values} \le \text{current})}{\text{Total Rows}}$.

SELECT ename, deptno, sal, CUME_DIST() OVER (PARTITION BY deptno ORDER BY sal) AS cumulative_dist FROM Emp;

6. LAG(expression, offset, default)

Previous Row

Returns a value from a previous row in the ordered window. Essential for computing time-series deltas and growth rates.

-- Display each employee salary along with the salary of the previously hired employee in same dept SELECT ename, deptno, hiredate, sal, LAG(sal, 1, 0) OVER (PARTITION BY deptno ORDER BY hiredate) AS prev_hired_emp_sal FROM Emp;

7. LEAD(expression, offset, default)

Following / Next Row

Returns a value from a following/next row in the ordered window. Used for forward target labeling in ML.

-- Display each employee along with the name of the next employee hired in same dept SELECT ename, deptno, hiredate, LEAD(ename, 1, 'NONE') OVER (PARTITION BY deptno ORDER BY hiredate) AS next_hired_employee FROM Emp;

8. FIRST_VALUE(expression)

Window Peak

Returns the value from the first row of the specified ordered window.

-- Display every employee along with the name of the highest paid employee in their dept SELECT ename, deptno, sal, FIRST_VALUE(ename) OVER (PARTITION BY deptno ORDER BY sal DESC) AS top_paid_employee FROM Emp;

9. LAST_VALUE(expression)

Window Base

Returns the value from the last row of the window. Crucial Gotcha: You MUST include ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, otherwise the default frame terminates at CURRENT ROW!

-- Display every employee along with the name of the lowest paid employee in their dept SELECT ename, deptno, sal, LAST_VALUE(ename) OVER ( PARTITION BY deptno ORDER BY sal DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING ) AS lowest_paid_emp FROM Emp;

10. NTH_VALUE(expression, N)

Nth Specific Position

Returns the value from the Nth row of the specified window frame.

-- Display every employee along with name of the 2nd highest paid employee in their dept SELECT ename, deptno, sal, NTH_VALUE(ename, 2) OVER ( PARTITION BY deptno ORDER BY sal DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING ) AS second_highest_paid_emp FROM Emp;

11. SUM() OVER (PARTITION BY ...)

Calculates total sum of values within partition while keeping every original row visible.

SELECT ename, deptno, sal, SUM(sal) OVER (PARTITION BY deptno) AS total_dept_payroll FROM Emp;

12. AVG() OVER (PARTITION BY ...)

Calculates partition average without collapsing records, allowing direct employee-to-dept benchmarking.

SELECT ename, deptno, sal, AVG(sal) OVER (PARTITION BY deptno) AS dept_avg_sal, sal - AVG(sal) OVER (PARTITION BY deptno) AS diff_from_dept_mean FROM Emp;

13. COUNT() OVER (PARTITION BY ...)

Counts rows or non-null values across the partition.

SELECT ename, deptno, COUNT(*) OVER (PARTITION BY deptno) AS dept_emp_headcount FROM Emp;

14. MIN() & 15. MAX() OVER (PARTITION BY ...)

Returns the floor and ceiling extremes within the partition.

SELECT ename, deptno, sal, MIN(sal) OVER (PARTITION BY deptno) AS min_dept_sal, MAX(sal) OVER (PARTITION BY deptno) AS max_dept_sal FROM Emp;

16. MEDIAN(expression) OVER (...)

Middle Value

Returns the true statistical 50th percentile middle value, immune to extreme high/low salary outliers.

SELECT ename, deptno, sal, MEDIAN(sal) OVER (PARTITION BY deptno) AS dept_median_salary FROM Emp;

17. STDDEV(expression) OVER (...)

Standard Deviation / Spread

Measures salary dispersion around the department mean. High STDDEV indicates wide wage disparity.

SELECT ename, deptno, sal, STDDEV(sal) OVER (PARTITION BY deptno) AS salary_stddev FROM Emp;

18. VARIANCE(expression) OVER (...)

Statistical Variance (\(\sigma^2\))

Calculates the statistical variance of values within the partition ($\text{Variance} = \text{STDDEV}^2$).

SELECT ename, deptno, sal, VARIANCE(sal) OVER (PARTITION BY deptno) AS dept_salary_variance FROM Emp;

Subqueries: Single-Row, Multi-Row & Correlated

Mastering nested query execution, list matching with IN, quantitative comparison with ANY / ALL, and short-circuit evaluation with EXISTS.

🎬 Real-World Dramatic Story: Google AI Team Salary Equity Audit During an internal HR compensation calibration audit, Google's people analytics team needed to flag all engineers who were paid less than the average salary of their respective specialization. Because employee specialization averages differ dynamically, a Correlated Subquery re-evaluates the benchmark for each candidate engineer row by row!
Single-Row Subquery

Scalar Result Comparison

Inner query returns exactly 1 row & 1 column. Evaluated using scalar operators (= > < >= <= !=).

-- Find emps earning above company avg SELECT ename, sal FROM Emp WHERE sal > (SELECT AVG(sal) FROM Emp);
Multi-Row Subquery

Set & Quantifier Evaluation

Inner query returns multiple rows. Evaluated using IN, > ALL (greater than max), > ANY (greater than min).

-- Emps earning more than ALL salesmen SELECT ename, sal FROM Emp WHERE sal > ALL ( SELECT sal FROM Emp WHERE job = 'SALESMAN' );
Correlated Subquery

Row-by-Row Correlation

Inner query references outer query table alias. Executes iteratively for every candidate row in outer query.

-- Emps earning more than their OWN dept avg SELECT e1.ename, e1.sal, e1.deptno FROM Emp e1 WHERE e1.sal > ( SELECT AVG(e2.sal) FROM Emp e2 WHERE e2.deptno = e1.deptno );

1_feature_store.sql — Recency, Frequency, Monetary (RFM) & Velocity Feature Store Query SQL
-- ========================================================================= -- 1. SQL FEATURE STORE: CUSTOMER 360 RFM & CHURN RISK FEATURE EXTRACTION -- Uses CTEs, Window Aggregations, LAG(), and Conditional CASE Statements -- ========================================================================= WITH CustomerOrders AS ( SELECT customer_id, order_id, order_date, order_amount, payment_method, LAG(order_date, 1) OVER ( PARTITION BY customer_id ORDER BY order_date ) AS prev_order_date FROM orders WHERE order_status = 'COMPLETED' ), CustomerMetrics AS ( SELECT customer_id, COUNT(order_id) AS total_orders, SUM(order_amount) AS total_spend, AVG(order_amount) AS avg_order_value, MAX(order_date) AS last_order_date, MIN(order_date) AS first_order_date, AVG(order_date - prev_order_date) AS avg_days_between_orders FROM CustomerOrders GROUP BY customer_id ), SupportTicketsSummary AS ( SELECT customer_id, COUNT(ticket_id) AS total_support_tickets, SUM(CASE WHEN priority = 'URGENT' THEN 1 ELSE 0 END) AS urgent_tickets FROM support_tickets GROUP BY customer_id ) SELECT c.customer_id, c.signup_date, c.country, c.subscription_tier, COALESCE(m.total_orders, 0) AS frequency_orders, COALESCE(m.total_spend, 0.0) AS monetary_total_spend, COALESCE(m.avg_order_value, 0.0) AS avg_order_value, COALESCE(CURRENT_DATE - m.last_order_date, 999) AS recency_days_since_last_order, COALESCE(m.avg_days_between_orders, 0) AS purchase_cycle_velocity, COALESCE(s.total_support_tickets, 0) AS support_tickets_count, COALESCE(s.urgent_tickets, 0) AS urgent_tickets_count, -- Target Label: 1 if churned (no order in 90 days), 0 if active CASE WHEN (CURRENT_DATE - m.last_order_date) > 90 THEN 1 ELSE 0 END AS is_churned FROM customers c LEFT JOIN CustomerMetrics m ON c.customer_id = m.customer_id LEFT JOIN SupportTicketsSummary s ON c.customer_id = s.customer_id;

10 Tough SQL Technical Interview Questions

Directly extracted from the 125-page notes and senior Data Science interview loops at Google, Amazon, and Meta.

Q1. How do you find the Nth highest salary in a table with duplicate salaries?

Answer: Use DENSE_RANK() in a Common Table Expression or Subquery. Unlike RANK() which skips ranks on ties (1, 2, 2, 4), DENSE_RANK() assigns contiguous integer ranks (1, 2, 2, 3), guaranteeing that filtering by rank = N accurately retrieves the true Nth highest distinct salary.

Q2. What is the critical pitfall when using NOT IN with a subquery containing NULL values?

Answer: In SQL three-valued logic, WHERE col NOT IN (SELECT mgr FROM Emp) translates internally to col != val1 AND col != NULL. Because col != NULL evaluates to UNKNOWN, the entire compound AND condition evaluates to UNKNOWN/False, causing the query to return 0 rows! Fix: Always filter WHERE mgr IS NOT NULL or use NOT EXISTS.

Q3. Explain the exact difference between RANK(), DENSE_RANK(), and ROW_NUMBER().

Answer: For tie values [3000, 3000, 2000]:
• ROW_NUMBER() assigns unique sequential numbers [1, 2, 3].
• RANK() assigns identical ranks to ties and skips subsequent numbers [1, 1, 3].
• DENSE_RANK() assigns identical ranks to ties without skipping numbers [1, 1, 2].

Q4. How do you find employees whose salary is greater than the average salary of their respective department?

Answer: Using a Correlated Subquery or Window function: SELECT * FROM Emp e1 WHERE sal > (SELECT AVG(sal) FROM Emp e2 WHERE e2.deptno = e1.deptno); or with Window function: WITH DeptAvg AS (SELECT *, AVG(sal) OVER (PARTITION BY deptno) AS avg_sal FROM Emp) SELECT * FROM DeptAvg WHERE sal > avg_sal;

Q5. Why can't you use a column alias defined in SELECT inside the WHERE or HAVING clauses?

Answer: Due to SQL's Logical Order of Execution: FROM (1) -> WHERE (2) -> GROUP BY (3) -> HAVING (4) -> SELECT (5) -> ORDER BY (7). The WHERE and HAVING clauses are compiled and evaluated before the SELECT clause executes, meaning the column alias does not yet exist in memory when filtering occurs.
